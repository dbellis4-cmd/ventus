## Migration execution and correction

Exactly two uniquely timestamped migrations exist, with no obsolete schedule-table
migration or conflicting version. Both applied cleanly in this order through
`supabase db reset --local --yes` in the disposable workspace. The migration ledger
contains both expected versions. A deliberate transactional DDL failure also proved
that its temporary schema object was rolled back.

| `20261019000200_workspace_initialization.sql` | `e85ae57dd75845770de7eb8b4a075294abe4ae24a9f3cdbd9a53a16af1f6d2f6` |

Initial runtime testing stopped at workspace initialization with SQLSTATE 42501:
`permission denied for schema auth`. Although the original migration granted the
writer auth-schema USAGE, the grant was absent after the local reset/restart sequence.
This was a runtime permission failure, not a SQL/PLpgSQL compilation error.

Correction:

1. Added private `ventus_private.request_user_id()` using SECURITY INVOKER and a
   SQL-standard `RETURN auth.uid()` body parsed when the migration is defined.
2. Replaced runtime textual `auth.uid()` references in RPC/private helper bodies
   with this narrow delegation. Stored ownership RLS still uses standard `auth.uid()`.
3. Removed reliance on writer USAGE of the managed Auth schema. No additional
   definer, RLS bypass, table privilege, anonymous access or broad role inheritance
   was introduced. The existing postgres-owned account-erasure trigger is unchanged.
4. Reapplied from a clean local database and reran the complete executable suite.
   Metadata verifies the UID helper is invoker-only and has a pre-parsed SQL body.

[PostgreSQL SQL-function body behavior](https://www.postgresql.org/docs/current/sql-createfunction.html)
explains definition-time parsing. The revised static checker recognizes this safe
function form and still checks explicit function ownership/grants and five-table RLS.

## Reproduction and remaining scope

The harness is `supabase/tests/verify_local.py`. It requires a dedicated unlinked
`/private/tmp/ventus-m3-local-*` CLI workspace, the same five-service local stack
and ports, copies of these migrations, and a mode-0600 `local-status.json` captured
privately from local `supabase status --output json`. Never print or commit status
credentials. Run the harness with that workspace path only. It refuses other
API endpoints; all SQL observer commands pin the local Docker socket/container.
The temporary `run_cli.py` used here also rejects linked/remote/push/pull commands.
Do not point the application `.env.local` at this stack or reuse hosted credentials.

Remaining checks/decisions before relying on real user data or release:

- Hosted PostgreSQL version/platform compatibility is deliberately uninspected.
  Any later hosted migration requires separate authorization and compatibility review.
- Exhaustive boundary/fuzz cases, very large trees, query plans/load/performance and
  backup restoration are not established by the 132-assertion suite. PLAN.md retains
  these and additional adversarial cases as future work.
- No application persistence wiring or account-deletion interface exists yet.
  Future endpoints need session, origin/CSRF, recent reauthentication/MFA, confirmation,
  retry and user-facing error tests. The database cascade test does not verify them.
- Define operational bounds/category behavior details, anytime overdue cutoffs,
  cancellation reversal and privacy/backup retention where still unresolved.
- Recurrence, Calendar and gamification remain deferred. No policies/services were
  weakened or configured to implement those features during verification.
- Password recovery remains **pending manual verification due to Supabase rate
  limiting**. Local DB tests and mocked Auth tests do not mark it passed.
- No commits, pushes, hosted-project changes or deployment were performed.
