## Approved decisions to preserve

- Five core tables: `user_settings`, `categories`, `tasks`, `task_occurrences`, `task_activity`. Owner-matching relationships and strict RLS isolate users.
- Restricted writer role and narrow authorized RPCs perform atomic task/subtask writes with append-only history. Targeted hierarchy-root/occurrence locks and expected versions protect concurrency. Creation keys/fingerprints and occurrence uniqueness prevent repeated effects; no command-receipt replay framework.
- Original and current scheduling live on stable occurrences. Actual completion timestamps and recording timestamps remain distinct; reopening/corrections preserve prior events. Completing subtasks never automatically completes their parent.
- Default category names: Classes, Meetings, Assignments, Professional Events, Social Events, Personal Tasks, Miscellaneous. Custom categories can be created/renamed/archived; snapshots preserve historical category information. Lazy `initialize_workspace(timezone)` initializes settings/defaults once.
- Individual task deletion is soft deletion. Permanent account deletion must securely erase associated personal data through a future explicit server-only workflow; database cascades are implemented, but no deletion interface/endpoint exists.
- User-selected IANA zones; anytime tasks are local dates without fake midnight instants. Preserve original slots; account-zone changes do not move existing schedules. Reject DST gaps and explicitly resolve ambiguous offsets.
- Standard Supabase SSR sessions permit browser-side user-session tokens. Privileged credentials and Google OAuth tokens stay server-only. Normal task requests must use the verified user's session, never an elevated key.
- Recurrence operations are explicitly rejected until Milestone 4. Separate schedule revisions, complex response replay and gamification infrastructure are deferred.

Refresh tokens are encrypted with AES-256-GCM in a service-only Supabase table. Browser actions require the verified Ventus user and same-origin POST checks. Disconnect clears the stored token and leaves existing Google events.
- Top-level task preferences default from category settings, can be changed in the existing task editor, and are stored through owned RPCs. Recurring occurrences have independent link preferences; a Google deletion suppresses only its matching occurrence. Outbound writes use stable event IDs and private link metadata. Inbound changes use the existing version-checked task RPCs. Ventus wins simultaneous mapped-field edits; unsupported Google edits pause only their link for review. Completed task edits retain Ventus fields. Successful task writes schedule an outbound pass after the response; the daily recovery route retries outbound work within Vercel Hobby's once-daily cron limit. Google edits import on app open or manual sync.
- The forward-only `20261023000100_google_calendar.sql` migration was rebuilt from scratch on disposable local Supabase. The local test verified per-occurrence and future-series preferences, service-only candidate/recovery RPCs, two-account isolation, the dirty queue and re-enabling a suppressed link. Twelve fake-Google tests passed for mapping, token encryption/tampering, idempotency, uncertain insertion, cancellation, past-key postponement, inbound/outbound conflict, unsupported edits, expired cursors, reauthorization, recovery authorization and OAuth account binding. Existing 59 task and 17 auth tests, seven isolated Playwright tests, lint, typecheck and the Webpack production build passed. Ponytail review found and fixed timestamp equivalence, unsupported span, recovery queue access and disconnected-owner selection issues.
- Follow-up local OAuth setup created a dedicated Ventus calendar in the owner's Google test account. The first sync remained pending because `service_role` had no `SELECT` grant on `user_settings`, `tasks`, `task_occurrences` or `task_recurrence_revisions`. The pending migration now grants only the columns used by sync; the same grants were applied to the existing local database without resetting the connection. Database-backed regressions passed for service reads, denied service writes, anonymous and cross-account access, and the authenticated task RPC boundary. Twelve fake-Google tests, 59 task tests, 17 auth tests, lint, typecheck and Webpack build passed again; Playwright was not rerun for this SQL-only fix.
- Controlled live verification matched the local connection to an owned, non-primary Ventus Google calendar. One disposable Meetings task exported as exactly one event; a Google title edit imported and persisted after refresh. A second daily series now has exactly three events on October 25–27. An automation date-input issue initially saved it without an end date and created 100 link rows, 90 of which were observed active; the corrected series end date and a sync left only the three intended links active, with no extra events found through the one-year horizon. A Google title edit on October 26 imported only into that occurrence. Deleting the linked October 27 Google event suppressed only its link; the Ventus series survived, and a repeat sync did not recreate the deleted event. Unrelated calendars' events in the test window were unchanged. A later two-account test first used one shared Google identity and separate dedicated calendars, then two distinct Google identities. Shared-identity disconnect revokes the common Google grant and requires reauthorization of the other Ventus account; a one-Google-identity-per-Ventus-account product rule is recommended pending review.
